# Triage Rules

## Default assumptions

- If a blob of logs, stack traces, or pasted output appears without narrative, treat it as a current failure in the active repo or project until evidence says otherwise.
- Start from exact evidence, not generic diagnosis.
- Preserve original identifiers verbatim.
- Do not guess owners. If ownership is unclear, keep `Owner: Unknown` or leave the issue unassigned.

## Repo and language detection

- Resolve repo context from the local checkout first: `git rev-parse --show-toplevel`, `git remote get-url origin`, workspace folder names, and package or crate manifests.
- Infer the likely language and surface from both the artifact and the repo:
  - Rust: `Cargo.toml`, `.rs`, panic or backtrace output, cargo logs
  - TypeScript or JavaScript: `package.json`, lockfiles, `.ts/.tsx/.js`, Next/Vite/test output
  - Python: `pyproject.toml`, `.py`, traceback output
  - Go: `go.mod`, `.go`, panic output
- Prefer the smallest affected package, crate, app, or service instead of filing against the whole monorepo.

## Rephrase into a concise case

- Keep the title short, action-oriented, and seam-specific.
- Preserve exact error strings, routes, env vars, versions, and IDs in the body where they matter.
- Use precise terminology instead of pasted prose, but do not erase the original evidence.
- Useful title patterns:
  - Bug: `<surface>: fix <observable failure>`
  - Feature: `<surface>: add <new capability>`
  - Improvement: `<surface>: improve <current behavior>`
  - Investigation: `<surface>: investigate <symptom>`
  - Chore: `<surface>: clean up <maintenance task>`

## Issue body template

Every triage-authored comment and every issue body created directly from triage should start with:

```md
> *This was generated by AI during triage.*
```

Use this body structure for Linear descriptions and GitHub issues:

```md
> *This was generated by AI during triage.*

## Summary

One concise statement of the problem or request.

## Evidence

- exact error, route, version, or artifact reference
- exact repo, package, crate, or service seam

## Classification

- Type: Bug | Feature | Improvement | Chore | Investigation
- Scope: XS | S | M | L | XL
- Rough effort: brief prose or workspace estimate
- Severity: Sev0 | Sev1 | Sev2 | Sev3

## Acceptance

- concrete expected outcome
- validation seam or command when known

## Dependencies

- blocker or blocked-by links
- parent or child issue references
```

## Type decision rubric

- Bug: expected behavior is broken now, and the evidence points to a current failure or regression.
- Feature: net-new capability or product expansion. If it is clearly future work, case it for `n+1` and only set cycle or due date when the workspace already has a real release plan.
- Improvement: current behavior exists but should change or tighten.
- Chore: maintenance, tooling, dependency, docs, or cleanup work.
- Investigation: evidence warrants work, but the actual fix or boundary is not yet well enough defined.
- If the workspace only has `bug` and `enhancement`, map Feature, Improvement, and Chore to enhancement and explain the finer-grained type in the body.

## Scope and rough effort

- XS: one seam, obvious change, narrow validation
- S: one package, crate, app, or service surface
- M: one cross-layer flow or several tightly related files
- L: multi-surface or order-dependent work across packages or services
- XL: project-sized or still too broad to implement safely as one issue
- If the Linear estimate scale is unknown, keep the prose size and leave numeric estimate unset.
- If the workspace uses Fibonacci estimates and the user wants a number, map XS=1, S=2, M=3, L=5, XL=8.

## Severity and priority

- Sev0 / Urgent: outage, data loss, security break, auth break, or release blocker
- Sev1 / High: core flow broken without a reasonable workaround
- Sev2 / Normal: degraded behavior, partial breakage, or workaround exists
- Sev3 / Low: minor defect, polish, docs, or tooling issue
- Use severity in prose even if the tracker only exposes priority fields.

## Duplicate and stale handling

- Search Linear with exact error strings, route names, feature nouns, repo or module names, and quoted phrases.
- Read matching issues, comments, and child issues before deciding.
- If an existing issue is correct and still active, enrich it instead of cloning it.
- If an issue was closed or completed incorrectly, move it back to an active state, append fresh evidence, and reference the earlier closeout.
- When reviving an old or stale issue, mention the original creator or original assignee if they are the most relevant context holder.
- Only mark something as duplicate when the remediation path is materially the same.

## Parent-child and blocker rules

- Create a parent issue when more than one language, package, service, or deployable step is involved.
- Create child issues when the work can be implemented or validated independently.
- Put foundational work in blockers first, then wire dependent issues with `blocks` or `blockedBy` immediately.
- Prefer a small dependency tree over a flat backlog.
- Each child issue should stand on its own with goal, affected surfaces, acceptance criteria, dependencies, and validation.

## Linear workflow

- Discover the actual `linear` tools first.
- Read first: search, list issues, list comments, list statuses, and list labels as needed.
- Then write: create or update the parent issue, then child issues, then blocker links, then comments.
- Confirm team, project, label, and state names from the current workspace before inventing them.
- If you touch multiple issues, close out each issue before moving to the next.

## GitHub workflow

- Resolve the repository from the local checkout first.
- Verify auth with `gh auth status`.
- Optionally scan for nearby GitHub issues with `gh issue list --state all --search "<query>"`.
- Create GitHub issues only after the Linear structure is stable.
- Prefer one GitHub issue per actionable engineering work item, not per conversation fragment.
- If GitHub MCP exposes a better issue creation surface than `gh`, use it; otherwise use `gh issue create`.
